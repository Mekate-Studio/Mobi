## CVE scope and three runtime choices

The [Oracle-assigned CVE record](https://www.cve.org/CVERecord?id=CVE-2026-114938)
describes the affected compiler component and API-input condition. The
[Zulu advisory](https://support.azul.com/hc/en-us/articles/55793255806100-Java4Shell-for-Zulu-and-Zing-CVE-2026-114938)
limits the affected optimization to x86-64 CPUs exposing AVX-512 features;
ARM64, including Apple Silicon, is outside that affected architecture. Azul
identifies Zulu 25.38.201 / JDK 25.0.5.1+2 as fixed. The
[Temurin advisory](https://adoptium.net/news/2026/11/temurin-november-2026-cspu-java4shell)
likewise lists 25.0.5.1+2 and requires the affected x64 instruction set.

The inspected host is arm64, as were the previous native hosted qualification
images. Their passing tests cannot demonstrate remediation of an x64 intrinsic.
Other Android developer/CI hosts need their own CPU and selected-runtime review;
neither an affected version number nor an ARM result proves Mobi exploitability.
No exploit, mitigation JVM flag or global cache cleanup is introduced.

| Runtime owner | Selection and what 0.14.1 establishes |
| --- | --- |
| Managed CLI JRE | Consumer wrapper selects the distribution; its launcher selects a version-named JRE slot and checks the pinned extraction marker. Verified 0.14.1 bytes pin the fixed vendor build. |
| Explicit CLI JRE | `KOTLIN_CLI_JAVA_HOME` bypasses managed selection. The launcher does not upgrade that path. `JAVA_HOME` alone does not select the CLI JRE. |
| Compilation/project JDK | Separate provider uses the project's selection mode. In auto mode it accepts a matching-major `JAVA_HOME` or provisions a JDK. Successful provisioning is persistently cached; the CLI JRE pin does not establish that this selected JDK is patched. |

The [default compiler-runtime task](https://github.com/JetBrains/kotlin-toolchain/blob/f53674bce744f0b5e9ff235110dcc1d565d2c114/sources/amper-cli/src/org/jetbrains/amper/tasks/ProvideKotlinCompilerRuntimeTask.kt)
uses the separate provider. Its
[selection/cache implementation](https://github.com/JetBrains/kotlin-toolchain/blob/f53674bce744f0b5e9ff235110dcc1d565d2c114/sources/amper-jdk-provisioning/src/org/jetbrains/amper/jdk/provisioning/JdkProvider.kt)
prefers suitable `JAVA_HOME` in auto mode and caches successful provisioning
without a time expiry. The release warns that cached project JDKs may need an
explicit refresh. Actual project-cache reuse across a 0.14.1 native build is
still unqualified; this source review does not claim to reproduce that outcome.
Record the CLI JRE, compiler JDK, project JDK and host separately during testing.

## Cache-selection controls

Four one-off owned fixtures exercised the **unmodified published shell scripts**
with prepared cache sentinels, a fake Java executable and disabled network calls.
They test selection logic, not real archive extraction, JVM startup or app builds.

| Control | Observed result |
| --- | --- |
| 0.14.0 with old/new slots present | Selects the old managed slot. |
| 0.14.1 with old/new slots and old `JAVA_HOME` | Selects the new managed slot; ignores `JAVA_HOME` for this owner. |
| 0.14.1 with explicit old `KOTLIN_CLI_JAVA_HOME` | Uses the explicit old slot. |
| 0.14.1 with only the old managed slot | Requests the new pinned JRE URL and fails on the deliberately disabled download; does not fall back to the old slot. |

Every control preserved the old fixture slot. No user cache or consent state
was modified. These ignored one-off fixtures add no maintained runner.

## Remaining risk and next qualification

The four Jackson JARs and FUS's published serializer files are byte-identical
to 0.14.0. The [Jackson review](2026-11-21-toolchain-014-jackson.md) and its fresh
November 21 package observations therefore remain relevant, without implying
that unchanged bytes refresh all advisory evidence. Other retained findings,
unassigned artifacts and the Gradle 9.8 transform-observer gap remain open.
The JRE release supplies no Swift-export producer replacement; IOS-10 stays.

Before real candidate CLI/JRE or native execution, review an explicit **0.14.1-only experimental
qualification** decision bound to the publication timestamp and distribution
hash above. Retain the real `age_blocked` state. Adoption, risk acceptance,
signed delivery and workaround removal are separate decisions.

The first real-app qualification should add the exact reviewed wrapper pins and
an exact 0.14.1 producer case; the current producer deliberately accepts only
0.13.0/0.14.0. No new adapter is justified by this assessment. Keep Kotlin/exporter
2.5.0-RC, Metro, Swift packages, platform floors and behavior fixed. Verify actual
fresh and retained CLI/compiler-JDK selections in an owned workspace, then run
the existing Android/shared and native iOS checks with one Kotlin runtime,
record-version refusal, export controls and owned cleanup. Any unexpected
record/layout change needs its own review before relaxing a guard.

Existing cache-free jobs provide fresh-workspace evidence; they do not simulate
all retained developer caches. Use bounded owned copies for retained-cache
controls rather than deleting global caches or rewriting an explicit override.

The [compact receipt](2026-11-21-toolchain-0141-jre.json) binds the wrappers,
archive delta, selected JRE metadata, fixture outcomes and primary responses.
Full archives and entry inventories remain in ignored local evidence storage.
The application wrapper, candidate allowlist, policy and runtime configuration
are unchanged by this assessment.
